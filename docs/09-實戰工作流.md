# 09 · 實戰工作流

前面八章講機制，這章講**怎麼用**。

---

## 9.1 核心工作流：探索 → 計畫 → 實作 → 驗證

九成的任務都該走這四步。跳過前兩步是新手最大的效率損失來源。

### 第 1 步：探索（唯讀）

```
(Shift+Tab ×2 進入 plan mode)

我要在 checkout 流程加入折扣碼功能。
先不要寫任何程式碼——先讀懂目前的 checkout 是怎麼運作的，
告訴我：訂單金額在哪裡計算、有沒有現成的優惠機制、資料表長什麼樣。
```

大型 repo 可以派子代理避免塞爆 context：

```
用 Explore 子代理找出所有跟訂單金額計算相關的檔案，medium 廣度就好
```

### 第 2 步：計畫

```
根據你剛才的理解，給我實作計畫：
- 要改哪些檔案，各自改什麼
- 資料庫要不要 migration
- 有哪些邊界情況（過期、疊加、最低消費）
- 測試策略

先不要動手。
```

**這一步花的 5 分鐘，通常省掉半小時的返工。**
計畫模式產出的計畫會存在 `~/.claude/plans/`。

### 第 3 步：實作

核准計畫後自動切回一般模式。大任務建議切段：

```
先做第 1、2 步就好，完成後停下來讓我看
```

### 第 4 步：驗證

```
跑測試
```

```
用 /code-review 看一下這次的改動
```

```
/run   ← 實際把 app 跑起來，確認不是只有測試會過
```

## 9.2 三種提問模式

### 給範圍

❌「這個專案有什麼可以改進的？」
✅「看 `src/api/orders.ts`，找出錯誤處理不完整的地方」

### 給驗收標準

❌「加個快取」
✅「幫 `getUser()` 加 in-memory 快取，TTL 5 分鐘，
　　使用者資料更新時要失效，並補上測試證明失效有效」

### 給禁區

```
可以改 src/ 和 tests/。
不要動 migrations/、不要動 package.json、不要 commit。
```

## 9.3 除錯流程

```
【現象】結帳偶爾會重複扣款，大概每 200 筆 1 次
【線索】只在流量高的時候發生；Sentry 上看到 charge_id 重複
【要求】先只調查不修改。找出根因，告訴我是哪一段程式在什麼條件下會出問題。
```

Claude 給了假設之後：

```
你怎麼確定是這裡？給我證據——貼出關鍵程式碼，並說明時序上怎麼交錯才會觸發。
```

**要求證據**是最有效的一招。它會逼 Claude 回去驗證而不是猜。

修正後：

```
寫一個測試來重現這個 bug（應該要 fail），跑一次確認 fail，再修，再跑一次確認 pass
```

## 9.4 大型 repo / monorepo

### 分層 CLAUDE.md

```
monorepo/
├── CLAUDE.md                    共通：工具鏈、發版流程、跨套件慣例
├── apps/web/CLAUDE.md           前端專屬（讀到這裡的檔案才載入）
├── apps/api/CLAUDE.md           後端專屬
└── packages/ui/
    ├── CLAUDE.md
    └── .claude/skills/          這個 package 專屬的 skills
```

好處：根目錄那份保持精簡，細節只在相關時載入。

### 排掉別人的

```json
// .claude/settings.local.json
{ "claudeMdExcludes": ["**/other-team/**/CLAUDE.md"] }
```

### 從子目錄啟動

```bash
cd apps/api && claude       # 只載入根 + apps/CLAUDE.md + apps/api/CLAUDE.md
```

## 9.5 Code review 流程

```
# 審目前的 diff
/code-review

# 審某個 PR
/code-review 482

# 提高深度
/code-review high

# 審完直接套用修正
/code-review --fix

# 把意見貼成 PR 的 inline comment
/code-review --comment
```

level 說明：`low`/`medium` 少而準；`high`→`max` 涵蓋廣、可能包含不確定的項目。

安全審查另有 `/security-review`；純品質清理（不抓 bug）用 `/simplify`。

## 9.6 Git 工作流

```
看一下我的改動，幫我拆成幾個邏輯清楚的 commit
```

```
把這次改動開成 PR，描述裡說明「為什麼」而不只是「改了什麼」
```

自訂 `/commit` skill（見 [04 章](04-Skills-技能.md)）之後，統一格式最省事。

**建議設定**：

```json
{
  "permissions": {
    "allow": ["Bash(git status)", "Bash(git diff *)", "Bash(git add *)", "Bash(git log *)"],
    "ask":   ["Bash(git commit *)"],
    "deny":  ["Bash(git push --force*)", "Bash(git reset --hard *)"]
  }
}
```

## 9.7 CI / 自動化

### 無頭模式

```bash
# PR 自動 review
claude -p "審查這個 PR 的變更，只回報高信心的正確性問題，用 markdown 條列" \
  --output-format json > review.json

# 每日相依套件檢查
claude -p "檢查 package.json 有無高危漏洞，有的話列出來，沒有就回 OK"
```

CI 環境建議：

```bash
claude -p "..." \
  --permission-mode dontAsk \
  --no-session-persistence
```

### 排程

```
/schedule 每個工作日早上 9 點，檢查 main 分支的 CI 狀態，失敗的話摘要原因
```

### 迴圈

```
/loop 5m 檢查 deploy 狀態，完成或失敗時通知我
/loop 檢查 PR #482 有沒有新 review（不給間隔＝由模型自己決定節奏）
```

## 9.8 context 管理

一個 session 的 context 是有限的。三個習慣：

**1. 任務結束就 `/clear`。** 不相關的歷史只會干擾判斷。

**2. 快滿時手動壓縮並指定重點。**

```
/compact 保留 API 設計的決策和還沒做完的 TODO
```

**3. 大量讀取的工作派給子代理。**

用 `/context` 隨時看目前的分配。發現 CLAUDE.md 佔太多，就該搬去 Skill 或 rules。

## 9.9 把設定養成團隊資產

建議的採用順序：

**第 1 週**
```bash
/init                          # 產生 CLAUDE.md，人工修訂
/fewer-permission-prompts      # 產生權限白名單
git add CLAUDE.md .claude/settings.json && git commit
```

**第 2–4 週**：注意自己重複打了什麼
- 重複的**指示** → 進 CLAUDE.md
- 重複的**流程** → 變成 Skill
- 重複的**提醒**（「記得跑 lint」）→ 變成 Hook

**第 2 個月**：CLAUDE.md 超過 200 行了
- 拆到 `.claude/rules/`，加上 `paths:`
- 大型調查任務寫成子代理

**第 3 個月**：多個專案在用同一套
- 打包成 Plugin，放內部市集

### 新人上手檢查清單

```markdown
- [ ] clone repo 後先看 `.claude/`（尤其 skills 的 allowed-tools 與 hooks）
- [ ] 跑 `claude` 並信任目錄
- [ ] `/context` 確認 CLAUDE.md 載入了
- [ ] `/help` 看團隊有哪些自訂 skills
- [ ] 第一個任務用 plan mode 走一遍
```

## 9.10 反模式

| 反模式 | 為什麼不好 | 改成 |
| --- | --- | --- |
| 「幫我優化這個專案」 | 沒範圍，會亂改一通 | 給明確檔案與目標 |
| CLAUDE.md 塞 500 行 | 吃 context，遵循率反而降低 | 拆 rules + skills |
| 全程 `bypassPermissions` | 沒有安全網 | 設好 allow 白名單就夠了 |
| 一個 session 做一整天 | context 被無關歷史稀釋 | 每個任務 `/clear` |
| 靠 CLAUDE.md 強制流程 | 它只是建議，會被忽略 | 用 hook |
| 不看 diff 就接受 | 你要為程式碼負責 | 至少掃一遍，或跑 `/code-review` |
| 直接叫它改，不先讀 | 它會邊改邊猜 | 先 plan mode |
